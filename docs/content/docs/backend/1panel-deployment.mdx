# 1Panel 编排部署

使用根目录 `docker-compose.1panel.yml`，环境变量模板为 `1panel.env.example`。这是单独的完整编排，不需要叠加 `docker-compose.deploy.yml`，也不要追加到旧 YAML 末尾，避免重复的 `services` / `volumes`。包含 PostgreSQL 17、Redis 7.4、一次性迁移、后端和网页服务。

## 镜像前提

默认镜像仓库是本地分支对应的 `ghcr.io/buttonslaybaugh397-art`，不会切换到上游仓库。`CANVAS_IMAGE_TAG` 默认 `latest`，前端、后端和迁移统一使用这一标签；未设置或留空也采用该默认值。需要固定版本时可设置实际发布成功的共同 `sha-xxxxxxx` 标签。`latest` 指我们仓库已发布的镜像，不代表本机未发布源码；编排本身不构建或发布镜像。

本模板依赖当前后端的 `migrate-schema up/verify` 和 `/api/health/ready`，不是旧镜像回退模板。发布工作流只在推送 `main`、`v*` 标签或手动触发时运行；只推送 `codex/*` 分支不会生成镜像。手动在开发分支运行可发布共同 SHA 标签，但不会更新 `latest`。`main` 的发布才更新 `latest`，前后端清单仍分别发布，必须确认两者均成功且对应同一提交后再更新编排。使用私有镜像时，在 1Panel 配置 GHCR 拉取凭据，不把凭据写进编排。

## 1Panel 配置

先区分部署入口：下面的原模板需要环境变量。已有五服务部署若使用 1Panel YAML 编辑器，可在本机运行 `bun 1panel-deploy/render-editor.mjs --env-file 1panel-deploy/.env --image-tag sha-<已发布完整提交SHA>`，生成私有 `.local/1panel-deploy/docker-compose.editor.yml`。它不依赖面板环境变量栏，沿用已解析的地址、端口、数据库名称和卷名，不包含数据库密码；原四个卷必须已存在，密码文件必须在原 secrets 卷中，否则拒绝启动。新安装继续使用原模板，不能使用编辑器升级文件。

生成器只执行 `docker compose config`，不调用 Docker daemon、不部署、不迁移、不覆盖输入或已有输出。运行前后均须核对本机配置是否确实对应目标服务器，尤其是四个卷及反向代理网络；不能把生成成功当作服务器配置已确认。私有输出不要提交仓库。

1. 在“容器 → 编排”创建或编辑编排，整份替换为 `docker-compose.1panel.yml`。
2. `CANVAS_CORS_ORIGINS` 在同源访问时可留空；如果网页与 API 是不同浏览器 Origin，再填写实际 Origin。`CANVAS_IMAGE_TAG` 保持默认 `latest` 即可，其余按 `1panel.env.example` 设置。不要使用通配 CORS。
3. 默认只绑定宿主机 `127.0.0.1:3000`，由宿主机 Caddy 监听 `80/443` 并反代到 `http://127.0.0.1:3000`。可直接使用仓库根目录或 `1panel-deploy/Caddyfile.example`，两份模板内容应保持一致。不要让 Caddy 直接代理 Backend 的 `8080`；Web 容器内的 Nginx 负责静态前端、`/api`、SSE、资源 Range 和 OAuth 回调。不要直接暴露 `3000`、`8080`、PostgreSQL 或 Redis 端口。
4. 仅作直接 IP 测试时，可设置 `CANVAS_BIND_ADDRESS=0.0.0.0`、`CANVAS_HTTP_PORT` 为实际测试端口，并将 CORS 设为实际 `http://服务器IP:端口`。生产使用 HTTPS；`CANVAS_PUBLIC_BASE_URL` 填真实 HTTPS 根地址，例如 `https://canvas.example.com`，不要填 `/api` 或容器地址。CORS 填浏览器访问域名的 Origin，不带路径、末尾斜杠或 `*`。
5. 保存启动。`postgres` 健康后运行迁移；迁移成功且 Redis 健康后启动后端；后端就绪后启动网页。`migrate` 退出码 0 是正常完成，不需要一直运行。

外层 Caddy 应保留 `Host`、`X-Forwarded-Proto`、`X-Forwarded-Host` 和 `X-Forwarded-For`。文本事件流及明确的模型 SSE 路径需要及时 flush，模板只对这些路径设置 `flush_interval -1`，不要对所有 API 关闭缓存和缓冲。

## 旧 6868 入口迁移到 Caddy

这次迁移只切换 Web 的宿主机入口，不搬迁 PostgreSQL、Redis、上传文件、`.settings-key` 或 secrets 卷。迁移期间让旧 `6868` 和新 `3000` 双入口并存，先验收 Caddy，再移除旧入口。数据卷、账号、登录态配置和应用内网链路保持不变。

如果当前 1Panel 的 OpenResty 已占用宿主机 `80/443`，把网关所有权交给 Caddy 仍需要一个很短的交接窗口。没有前置负载均衡器、第二公网 IP 或备用节点时，不能承诺网关层绝对零中断；这里的无缝迁移指应用数据和服务链路不变，并把中断压缩到网关交接。

### 一键迁移脚本

服务器已经安装 Caddy、Docker Compose v2，并且 Caddy 由 systemd 管理时，可以直接执行：

```bash
sudo bash 1panel-deploy/migrate-to-caddy.sh \
  --project-dir /opt/1panel/compose/open-ai-canvas \
  --domain canvas.example.com \
  --takeover-service openresty \
  --yes
```

`--project-dir` 必须是当前 1Panel 编排实际使用的目录，里面应有原 `.env` 和 Compose 文件；如果当前网关是 Docker 容器，改用 `--takeover-container <容器名或ID>`。脚本会复用当前 Compose 项目和四个已有卷，备份配置到 `/var/backups/open-ai-canvas-caddy/<UTC时间>/`，临时增加 `127.0.0.1:3000`，验证 Caddy 和真实 HTTPS 健康检查后，再把 `CANVAS_HTTP_PORT` 收口为 `3000`。它不会执行 `docker compose down -v`，不会删除卷，也不会停止 Backend、PostgreSQL 或 Redis。

如果 `/etc/caddy/Caddyfile` 已有其他站点内容，脚本默认拒绝覆盖；确认它是本应用专用配置后再追加 `--replace-caddyfile`。

DNS 或证书尚未就绪时可加 `--skip-public-check`，但之后必须手工验证真实 HTTPS 域名。脚本失败会尝试恢复原 `.env`、Web 旧端口、Caddy 配置和旧网关；失败后仍应检查备份目录与服务状态。Caddy 未安装或不是 systemd 服务时，先完成宿主机 Caddy 安装，再执行脚本。

1. 备份 PostgreSQL、后端数据目录、`.settings-key` 和 Redis AOF；从旧容器挂载信息核对四个真实卷名。保留旧私有 `.env`，不要执行 `down -v`，不要新建第二套 PostgreSQL。
2. 旧入口继续保持 `CANVAS_HTTP_PORT=6868`，补齐真实的 `CANVAS_CORS_ORIGINS` 和 `CANVAS_PUBLIC_BASE_URL`，并固定前后端均已发布的共同镜像标签。若这次同时升级应用版本，数据库迁移仍按本页“更新与排障”执行，不要把路由切换当作数据库回滚。
3. 在本机用当前旧配置生成临时桥接编排：

   ```bash
   bun 1panel-deploy/render-editor.mjs \
     --env-file 1panel-deploy/.env \
     --image-tag sha-<已发布完整提交SHA> \
     --add-http-port 3000 \
     --output .local/1panel-deploy/docker-compose.caddy-bridge.yml
   ```

   生成文件会保留旧的 `127.0.0.1:6868:3000`，并增加 `127.0.0.1:3000:3000`；四个已有卷会被标记为 `external: true`。在 1Panel 中整份替换 YAML，不要把它追加到旧文件末尾，也不要修改卷名、数据库名称或密码。若现有端口不是 `6868`，以服务器实际端口为准，命令中的 `--add-http-port 3000` 仍只增加 Caddy 新入口。
4. 在宿主机准备 Caddy 配置，将站点地址替换为真实域名，先运行 `caddy validate --config /etc/caddy/Caddyfile`。确认 `curl -fsS http://127.0.0.1:3000/` 成功后，安排网关交接：停止或移除 1Panel 站点对 `80/443` 的占用，启动并 reload Caddy。不要先停止 PostgreSQL、Redis 或 Backend。
5. 用真实 HTTPS 域名验证证书、登录与 Cookie、`/api/health/ready`、文本 SSE、资源 Range、上传访问和已有任务恢复。旧 `6868` 入口在此阶段仍可作为回退入口。
6. 验收通过后，将私有环境中的 `CANVAS_HTTP_PORT` 改为 `3000`，重新生成**不带** `--add-http-port` 的最终编辑器编排，再整份替换 1Panel 配置并只重建 Web。确认 `6868` 不再被使用后，删除旧 1Panel 反向代理站点。

如果迁移中止，先停止 Caddy 并恢复旧 1Panel 站点，再继续使用 `6868`；不要回滚数据库迁移，也不要删除任何卷。若同时发生 schema 升级，应用回退必须使用与数据库版本匹配的镜像和备份，不能只改回旧标签。

## 旧数据库与密钥

默认固定命名卷与早期 `open-ai-canvas` 编排一致，避免 1Panel 改变项目名称后意外换成空卷。更新前仍须在旧容器“挂载”中核对实际名称，并先做完整备份：

| 环境变量 | 默认卷 | 内容 |
| --- | --- | --- |
| `CANVAS_POSTGRES_VOLUME` | `open-ai-canvas_postgres-data` | PostgreSQL 17 数据文件 |
| `CANVAS_BACKEND_VOLUME` | `open-ai-canvas_backend-data` | 上传文件、平台配置加密文件 `.settings-key` 等 |
| `CANVAS_SECRETS_VOLUME` | `open-ai-canvas_deployment-secrets` | PostgreSQL 密码及连接串 |
| `CANVAS_REDIS_VOLUME` | `open-ai-canvas_redis-data` | Redis AOF 持久数据 |

卷不存在时 Docker 会创建新卷，因此不能把模板默认值当作已经识别到真实数据。旧部署若使用宿主机目录挂载，需要按旧容器实际挂载修改相应 `volumes`，不要把目录路径填进上述卷名变量。不能将 SQLite 文件、SQL dump 或备份压缩包直接挂到 PostgreSQL 数据目录；也不能把其他 PostgreSQL 主版本的数据目录直接交给 17 使用。

首次全新部署会生成 48 位随机十六进制密码，后续重建继续读取 secrets 卷，不会重新生成覆盖。如果已经存在 PostgreSQL 数据但密码文件丢失，启动明确失败，需还原对应 secrets 卷或提供原 `POSTGRES_PASSWORD`。手动密码至少 32 位且只允许字母和数字；已有密码不能通过修改环境变量完成轮换。此约束沿用此前自动密码编排，不支持将其他格式的现有密码直接套入模板。

密码文件只挂载给 PostgreSQL、迁移和后端；Redis、网页都不挂载。为兼容这几个镜像中的不同 UID，文件模式为 `0444`，不是 Docker 原生加密 secrets；必须保护宿主机 Docker 管理权限和备份，不能把 secrets 卷挂给不可信容器。平台配置密钥在后端数据卷的 `.settings-key`，不是数据库密码文件；缺少匹配密钥会导致存储或渠道凭据无法解密。

不要删除旧卷、不要执行 `docker compose down -v`，不要通过清空 Redis AOF 修复启动错误。更新完成后也不要盲目回退应用镜像，因为数据库 schema 可能已经前进。

应直接更新原编排，不要让两套 PostgreSQL 容器同时使用同一个数据卷。换编排名称或迁移到新项目之前，确认原服务已停用并核对实际卷名。

## 更新与排障

### 本次 schema 27 → 29 升级

不需要新增服务、端口或数据卷，也不需要更换 PostgreSQL 17 / Redis 7.4。版本 28 增加 Agent 执行日志、消息和任务/计费授权字段，版本 29 增加审批资源租约。两份 1Panel YAML 保持一致，迁移命令现在执行 `up` 后再执行 `verify`；缺失或空连接文件立即失败，不继续启动。

1. 等待我们仓库目标提交的前后端镜像都发布成功。建议本次把 `CANVAS_IMAGE_TAG` 固定为两者共同的 `sha-<完整提交SHA>`，不要用仅在 Git 存在、尚未发布镜像的 SHA，也不要用带 `-amd64`、`-arm64` 或 `-multi` 的内部构建标签。
2. 核对并保留现有四个卷及私有环境变量，备份 PostgreSQL、上传资源和 `.settings-key`。确认当前没有需要继续等待的生成任务，按维护窗口停止旧 `web`、`backend`；依赖关系只控制启动，不能替你停止仍在运行的旧后端。
3. 拉取目标镜像并重新运行 `migrate`，确认 `up` 与 `verify` 均成功且期望版本为 29。不能只查看上一次已退出容器的旧日志，也不要只点击普通重启。
4. 迁移成功后再重建后端和网页。任何一步失败都停在该阶段并保留日志，不跳过迁移或改成后端自动迁移。

目录部署可在**现有部署的实际目录**执行下列顺序；前提是已完成备份、固定已发布标签且现有 PostgreSQL/Redis 正常。1Panel 编辑器模式应按同一顺序操作实际编排，不能在别的目录创建第二套服务。以下会停止应用和执行数据库迁移，不是只读检查：

```bash
set -e
docker compose --env-file .env -f docker-compose.yml config --quiet
docker compose --env-file .env -f docker-compose.yml pull migrate backend web
docker compose --env-file .env -f docker-compose.yml stop web backend
docker compose --env-file .env -f docker-compose.yml up --no-deps --force-recreate --exit-code-from migrate migrate
docker compose --env-file .env -f docker-compose.yml up -d backend web
```

根模板文件名为 `docker-compose.1panel.yml`，使用它时替换上述 `-f` 参数。不要执行 `down -v` 或替换 secrets 卷。迁移成功后旧后端会因 schema 不匹配拒绝启动，回退必须使用匹配的数据库备份和应用版本，不能仅改回旧标签。通用 `docker-compose.deploy.yml` 和上游一键脚本默认指向 `ddcat-ai`，不应拿它们覆盖这套本地增强版 1Panel 编排。

### 配置与健康检查

若就绪检查 200，但带实际 `Origin` 的请求返回 403「不允许的跨域来源」，先核对后端容器实际 `CANVAS_CORS_ORIGINS`，须包含协议、主机和非默认端口。修改配置后需更新编排重建容器；普通重启不会应用新的容器环境变量。

网页 Nginx 使用完整 `$http_host`（缺失时回退 `$host`）设置 `Host` 与 `X-Forwarded-Host`，修复旧 `$host` 丢端口导致的同源误判。普通 API、SSE、分享与 OAuth 回调统一处理，不信任客户端传入的转发主机头，也不采用通配 CORS。外层代理仍需保留公开端口；更新前可先配置准确白名单并重建后端。

若仍出现 `CANVAS_CORS_ORIGINS is missing a value`，说明 1Panel 仍使用旧的 `:?` CORS 模板，错误发生在 Compose 解析阶段，不是容器、镜像或数据库故障。整份替换为当前 `docker-compose.1panel.yml`；同源访问可以留空，跨域访问填写真实浏览器 Origin（协议、主机及非默认端口）。仅在本机修改 `.env` 或推送 `.env.example` 不会自动同步服务器，编辑器模式不要将 `KEY=value` 追加到 YAML。直接 IP 访问需同时使用 `CANVAS_BIND_ADDRESS=0.0.0.0` 与匹配的 HTTP 端口，生产仍应使用 HTTPS 和正确的反向代理网络。

1Panel 的环境变量栏和 YAML 是两个输入；仅替换 YAML 不会携带本机 `.env`。部分版本更新时会重写服务器 `.env`，留空可能丢失原配置；使用原模板时应保留完整环境配置，不能以 `.env.example` 覆盖原文件。编辑器升级文件已经固化所需配置，不依赖这一注入行为。

编排不挂载 Host Updater socket、Token 或 Docker socket，使用 1Panel 管理升级。迁移、后端和前端保留 `pull_policy: always`，但 1Panel 自己的预拉取阶段仍可能打印“使用存量镜像”；后续 Compose 才执行拉取策略，解析失败时尚未到这一步。更新时启用面板强制拉取并核对实际镜像版本，不凭提示认定已更新。普通重启不拉取，运行期间不自动更新。建议固定已发布的共同 SHA，避免前后端 `latest` 切换时间不一致。

Redis 保留 AOF 持久化、真实 PONG 检查，启动宽限为 120 秒，之后每 10 秒检查一次，最多 18 次连续失败。宽限只能容纳恢复耗时，不能修复权限、磁盘已满或 AOF 损坏。仍提示 unhealthy 时，先查看 Redis 容器日志和健康检查输出，保留原数据再按具体错误处理，不要把依赖降为 `service_started`。

迁移容器禁用继承的 HTTP 健康检查，必须成功退出才放行后端；迁移失败看 `migrate` 日志。旧 `migrate` 孤立容器警告本身不是 Redis 故障原因，本编排已明确包含该服务。

可先在服务器编排目录运行配置验证（只检查配置，不启动服务）：

```bash
docker compose --env-file .env -f docker-compose.1panel.yml config --quiet
```

验证登录、历史画布和资源、个人积分统计、渠道配置解密、生成轮询和任务持久化后再完成升级验收。健康检查通过不等于业务验证完成。

## 上传缓慢定位

浏览器到后端、后端到对象存储是两个阶段。进度 100% 只表示文件已传输，不能据此判断云端保存完成；视频还会先读取本地元数据和封面。当前视频封面与本体并行上传，大于 50 MiB 的文件使用最多 3 个并行分片；瞬时错误只重试失败分片，最多 3 次，不因合并失败自动重传整个文件。

在浏览器 Network 查看 `/api/resources` 或 `/api/resources/uploads/:id/complete` 响应的 `Server-Timing`，耗时单位为毫秒：

| 阶段 | 计时范围 | 排查方向 |
| --- | --- | --- |
| `receive` | 后端接收与解析上传体，分片接口为接收单片 | 上传带宽、后端临时盘；不包含前置代理缓冲 |
| `merge` | 分片校验完成后的合并与打开文件 | 临时盘性能、空间与 I/O 竞争 |
| `store` | 配额、存储配置、物理写入及数据库状态保存 | 数据库、服务端到对象存储的网络、S3 错误及重试 |

浏览器总耗时明显大于这些阶段时，还需核对视频解码、排队、1Panel 外层反向代理的请求缓冲及超时。没有拿到后端响应的请求可能没有 `Server-Timing`；不要据此判断存储正常。不要对所有 API 关闭缓冲或无限延长超时。

S3 PUT 的请求及重试共用 2 分钟上下文预算，最多重试 1 次，避免原先多轮各自超时导致长时间等待；这不是对象存储吞吐提速保证。当前已有降级策略在对象存储写入失败后将文件保存到后端本地，日志包含 `object storage upload degraded to local storage`。出现该日志时，上传成功不代表已经写入雨云，应核对该资源实际 `provider` 并保护后端数据卷，不能删除本地文件来排障。

改动需发布并更新同一提交的前后端镜像才生效。使用同一账号、同一文件记录大小、100% 前后耗时和失败响应；未进行真实服务器测量前，不将源码中的等待问题认定为线上唯一瓶颈。

## 迁移后画布资源引用报错

旧提示「画布媒体对应的云端资源不存在或尚未就绪」来自画布写入时的数据库校验，不是对象存储 HEAD 检查。后端要求画布引用的 Resource 属于当前用户且状态为 `ready`，同时存在匹配的 Asset；只复制 OSS / S3 文件不会补齐数据库记录。新提示区分记录不可用与尚未就绪，并携带请求中的资源 ID，记录不可用不区分缺失与其他账号归属，避免泄露跨账号资源信息。

排查时用同一时间点的 PostgreSQL 备份核对画布 `storageKey` / `content`、`resources.id/user_id/status` 及 `assets` 关联；保留原始备份与浏览器缓存，不直接清空 IndexedDB，不将资源批量设为 `ready`，也不以同名文件猜测资源归属。切换存储应保持资源 ID 和对象 key，只更改已验证的存储配置引用。

前端打开画布先完成远端详情与素材校验，再启动编辑态保存及历史任务恢复。生成结果入库只确认本次素材，不连带保存其他画布；画布批量保存中的单个写入失败不再阻塞其余画布，失败项保留未确认状态并继续抛错。当前画布的失败显示独立保存提示，相同错误不会随每次重试重复弹出，成功保存后清除。源码修复不能恢复备份中不存在的记录或物理文件，仍需从可核实的原始备份或原文件补齐。
