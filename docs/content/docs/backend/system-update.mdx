# 在线更新与安全回退

管理后台的“系统配置 → 系统更新”只负责管理员鉴权、展示状态和发起操作。真正的 Docker、数据库备份与服务切换由宿主机上的 `open-ai-canvas-host-updater` 执行，业务后端不挂载 Docker Socket。

```text
管理员浏览器 → Backend 管理 API → 带 Token 的 Unix Socket → Host Updater → Docker Compose
```

## 安全更新顺序

1. 从 GitHub Releases 读取包含预览版在内的最高语义版本。自动配置模式先从实际 Compose 同步镜像版本、项目名、端口和数据库元数据，再比较当前版本。
2. 下载指定的生产 Release 编排（标准部署或 1Panel），保留服务器原有项目名、数据卷、数据库连接、端口和内联环境配置，执行 `docker compose config --quiet` 并检查磁盘与当前版本。迁移服务使用同一数据库连接，不回退到模板默认账号。
3. 拉取目标 backend/web 镜像并要求存在仓库 `sha256` 摘要。任何失败都在停服前中止。
4. 停止 web/backend，等待 Backend 的 SIGTERM drain 完成；随后固化并停止 Redis，保证文件恢复点一致。
5. 创建 `backup-YYYYMMDD-HHMMSS.zip.partial`，其中包含 PostgreSQL custom-format dump、后端数据目录 tar、Redis 数据目录 tar、1Panel 部署密钥卷、部署 `.env`、当前 Compose 和元数据；写入完成后 `fsync`、原子改名，并复核 ZIP 结构和 SHA-256。
6. 用目标 backend 镜像独立执行 `migrate-schema up`。整批迁移在事务和 PostgreSQL advisory lock 内完成，迁移名称与 checksum 必须匹配。
7. 原子更新 `CANVAS_IMAGE_TAG` 和 Compose 文件，启动目标版本。
8. 连续检查 `/api/health/ready` 的数据库、运行时、schema 和 build version，并经过稳定窗口后才标记成功。

更新状态写入 `/var/lib/open-ai-canvas-updater/state.json`。Backend 或浏览器在切换期间断线不会终止宿主机操作，恢复后可继续读取日志。

## 自动回退

停服后的迁移、启动或健康验证失败会触发自动回退：

1. 停止目标 web/backend；
2. 再次校验恢复包 ZIP、SHA-256、PostgreSQL dump 和各数据归档；
3. 恢复包中的 `.env` 和 Compose，并校验恢复后的 Compose；
4. 恢复 1Panel 部署密钥卷，使用 `pg_restore` 重建 PostgreSQL，并恢复后端 `/data` 与 Redis 数据；
5. 恢复旧 `CANVAS_IMAGE_TAG`，启动旧服务并重新进行稳定窗口验证。

回退任一步失败时状态变为 `manual_intervention`，不伪造成功。管理后台仅在存在旧版本和已校验备份时开放人工回退按钮。

## 安装与升级约束

支持两种运行方式：Linux/systemd 宿主机服务，或 Release 附带的独立 Compose `host-updater` 容器。两种方式都要求 Docker Compose 和 PostgreSQL；systemd 模式无需手工挂载 `open-ai-canvas-host-updater-linux-amd64`，Compose 模式无需下载二进制。无论哪种方式，backend 都不应挂载 Docker Socket。

自动配置会拒绝外部数据库、不持久化的数据目录和不匹配的数据库连接；backend 数据目录须为 `/data`，PostgreSQL/Redis 也须使用对应持久挂载，防止备份指向另一套空数据。

在 1Panel **当前实际使用的编排目录**运行一次下面的命令。常规安装目录才使用示例中的 `/opt/open-ai-canvas`：

```bash
cd /opt/open-ai-canvas
curl -fsSL https://raw.githubusercontent.com/buttonslaybaugh397-art/open-ai-canvas/main/scripts/install-host-updater.sh | sudo bash
```

脚本自动识别目录中唯一的 Compose 文件、镜像所有者、已固定的应用版本及对应生产模板，下载最新正式 Release 的 Linux amd64/arm64 更新器并核对 `SHA256SUMS`。更新器版本独立选择，因此旧应用也能使用新的自动配置安装功能；可通过 `CANVAS_UPDATER_RELEASE_TAG` 显式固定更新器 Release，不会因此升级已经固定的应用版本。

脚本自动向 backend 添加 Socket 路径、Token 文件路径及只读目录挂载，生成随机 Token 并创建 systemd 开机自启服务。新 Token 只保存到 `/etc/open-ai-canvas-updater.env`（root-only）和运行目录的 Token 文件，不新复制到部署 `.env` 或容器环境；已有 `.env` 的无关设置不被清理。systemd 每次启动恢复 `/run` 内的 Token，再启动更新器创建 Socket。安装最后验证宿主机认证和 backend 挂载，不输出凭据。

无需预先创建 `.env`：运行设置直接填写在编排的 `environment`、`ports`、`image` 中。自动配置生成的 `.env` 保存版本、项目名、端口、数据库名称和更新器设置等恢复元数据；后续检查/更新会重新读取 Compose，不能把生成的元数据当作另一份需要手工维护的配置。

自动配置使用 Docker Compose 规范化 YAML，**会展开变量、YAML 锚点与 `env_file`，不保留原注释和排版**，解析后的环境值保存在原 Compose 中。原文先备份到 `backups/compose-before-configure-*.yml`，新 Compose 限制为 `0600`。这些文件可能包含密钥，都应按敏感配置管理。存在多个候选编排时安装会拒绝猜测，请明确指定原文件；1Panel 若保留编辑器草稿，后续操作前应重新打开服务器上的当前编排，避免旧草稿覆盖自动挂载。

## Compose 容器模式

不使用 systemd 的服务器可直接部署 Release 中的 `docker-compose.container.yml`。编排会自动启动 `host-updater`，在 named volume `updater-runtime` 中生成并持久化 Token 与 Unix Socket，在 `updater-state` 中保存更新状态和恢复信息；backend 通过只读挂载访问运行时目录，并等待更新器健康后再启动。Docker Socket 只挂载到 `host-updater`，这是该模式唯一的高权限边界。

```bash
cd /opt/open-ai-canvas
sudo docker compose -f docker-compose.container.yml config --quiet
sudo docker compose -f docker-compose.container.yml up -d --wait --wait-timeout 600
```

默认宿主机项目目录必须是 `/opt/open-ai-canvas`。更新器容器会在容器内以同一绝对路径作为 Compose 项目目录，Docker 守护进程随后也会按这个路径解析 bind mount；如果 1Panel 的实际目录不同，只需修改编排顶部 `x-canvas-project-dir` 的值为宿主机真实绝对路径，并把 `CANVAS_UPDATER_COMPOSE_FILE` 填为 1Panel 实际保存的文件名（通常是 `docker-compose.yml`）。不要把宿主机路径写成容器内路径，也不要用相对路径。

该文件中的应用镜像固定到发布版本，`host-updater` 默认关闭自更新，避免更新过程中替换正在执行的高权限容器；应用更新完成后如需升级更新器，重新拉取对应版本的 `docker-compose.container.yml` 并单独重建 `host-updater`。每次应用更新仍会在停写后生成完整恢复包，迁移、启动或健康检查失败会自动回滚；不要执行 `docker compose down -v`，否则会删除恢复所依赖的数据卷。

如果从已有 1Panel 编排切换到容器模式，必须保持 Compose 项目名和 PostgreSQL、Redis、backend-data、deployment-secrets 等卷的实际名称一致。自定义过 volume 名称时，先按服务器现有名称调整编排；名称不一致会让 Compose 创建新空卷，不能把“容器启动成功”当成“数据已接上”。

安装脚本会拉取镜像并重建 backend/web，并非只读诊断命令。若应用标签为 `latest`，会固定到仓库最新正式 Release；生产部署应事先固定版本。已有更新/迁移正在执行或处于待人工恢复状态时，安装拒绝继续，不重写恢复状态。配置落盘失败会尝试恢复原 Compose 与 `.env`；整个首次安装流程不是完整数据备份/自动回滚事务，必须先保留业务恢复点。

如果后台显示“Host Updater 当前未连接”，先执行以下只读检查，确认宿主机服务和 backend 挂载状态，不要直接重装或更新：

```bash
sudo systemctl status open-ai-canvas-updater --no-pager -l
sudo journalctl -u open-ai-canvas-updater -n 60 --no-pager
sudo test -s /run/open-ai-canvas-updater/token
sudo test -S /run/open-ai-canvas-updater/updater.sock
sudo docker compose -f docker-compose.deploy.yml exec -T backend \
  sh -ec 'test -r /run/open-ai-canvas-updater/token && test -S /run/open-ai-canvas-updater/updater.sock'
```

1Panel 使用 `docker-compose.yml` 或 `docker-compose.1panel.yml` 时，将检查命令中的文件名替换为实际文件。安装能识别唯一文件；多文件目录可用 `sudo env CANVAS_UPDATER_COMPOSE_FILE=docker-compose.yml bash` 运行下载的安装脚本。不要为了匹配示例复制或改名正在使用的编排文件。仅修改 Compose 不能创建宿主机 systemd 服务，首次仍需运行一次安装命令。排查时不要公开 Token、环境文件或其他凭据。

本地编排文件名与 Release 模板分开：检测到 `deployment-secrets` 卷时自动使用 `docker-compose.1panel.yml`，否则使用 `docker-compose.deploy.yml`。复杂自定义部署可显式设置 `CANVAS_UPDATER_RELEASE_COMPOSE_FILE`；不能使用仓库的开发编排。安装脚本支持通过 `CANVAS_IMAGE_TAG` 显式选择应用版本；除明确覆盖或原标签为 `latest` 外，保留现有应用版本。

Release 附件包含 `docker-compose.1panel.yml` 和 `install-host-updater.sh`。测试新版本前先创建可恢复备份，在原有编排项目内更新镜像和 Socket 挂载，保留项目名与全部数据卷。首次安装脚本不是在线更新事务，不提供完整备份及失败自动回滚，不能代替更新器连接后的在线更新流程。

## IP 与端口访问

内置 Web 代理已保留带端口的 `Host` 和 `X-Forwarded-Host`。同一站点经 `/api` 访问后端时，可直接在编排写 `CANVAS_CORS_ORIGINS: ""`，不再固定某个服务器 IP。现有校验按 Origin 与请求 Host/转发 Host 的主机和端口比较，并不是自动信任所有来源，也不是完整的 scheme 同源匹配。独立跨域前端仍需填写明确的 Origin。

生产必须使用 HTTPS，backend 不直接暴露到公网；额外的 1Panel/Nginx 反向代理须正确保留实际访问的 Host（包括端口），并覆盖而不是透传不可信的转发 Host。不要使用 `*` 绕过来源检查。

## 运维检查

```bash
sudo systemctl status open-ai-canvas-updater
sudo journalctl -u open-ai-canvas-updater -n 200 --no-pager
sudo ls -lh /opt/open-ai-canvas/backups
sudo sha256sum /opt/open-ai-canvas/backups/*.zip
```

备份文件包含业务数据、密钥和部署配置，应限制为 root 访问并纳入异机备份策略。数据卷本身不是备份。更新前会先停止 Web 与 Backend，保证数据库与文件数据处于一致恢复点；如果备份阶段失败，更新器会先恢复并验证更新前服务。

## 本地 SQLite 迁移

本地 Docker 编排不使用 PostgreSQL Host Updater，而是由独立运行的本地迁移助手调用固定的 scripts/migrate-local.ps1（Windows）或 scripts/migrate-local.sh（Linux/macOS）。管理后台会在“数据与服务迁移”区块中单独显示本地迁移能力；在线版本更新仍保持不可用。

本地迁移包包含 SQLite 数据目录、上传文件、.env、Compose/Docker 配置和当前已构建的前后端镜像。导入前会校验 ZIP 清单和 SHA-256，备份目标数据与配置；迁移失败会尝试恢复原状态。迁移助手只接受带 Token 的固定导出、导入和下载请求，不提供任意 PowerShell 或 Docker 执行接口。

```text
管理员浏览器 → Backend 管理 API → Token HTTP → host.docker.internal:9714
                                              → 固定本地迁移脚本 → Docker Compose
```

Windows 启动本地服务时，scripts/start-local.ps1 会构建并启动迁移助手；Linux/macOS 请运行 scripts/start-local-migration-helper.sh。两者都会将只读 Token 文件挂载到 Backend。若 Docker 或助手未运行，业务服务仍可启动，后台仅显示本地迁移不可用；请先检查 .local/migration-helper/helper.stderr.log 和端口 9714。
